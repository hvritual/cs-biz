# 后端设计说明

全局边界见 [架构设计](../../doc/architecture/README.md)。后端具体框架、存储技术和认证提供方仍需在首个运行切片落实。

## 模块职责

- `identity`：账户、登录、会话、认证提供方适配。
- `tenancy`：租户生命周期、成员关系、当前租户上下文。
- `entitlements`：租户已经生效的模块、额度和有效期；套餐目录与生效权益分开。
- `access`：角色、权限码、数据范围、有效权限查询及服务端鉴权。
- `audit`：记录谁在什么租户、何时对什么资源做了什么，关联操作 ID 与结果。
- 业务模块：客户、点位、设备、合同、服务等按已批准任务独立加入。

不预先为每个 CRUD 创建服务进程。先在模块化单体内保持清晰的依赖与事务边界，出现可度量的规模、隔离或团队需要时再拆分。

## 数据与权限

全局账户与租户成员关系分离；一个用户可属于多个租户。角色和数据范围受租户限定。任何查询、写入、后台任务、缓存、对象存储路径和导出都必须携带并校验租户上下文。

合并多个角色时，保持每项动作与其数据范围的绑定。禁止把某角色的全量读取范围和另一角色的局部写入权限组合成全量写入。列表、批量、导出和下载分别使用对应动作的范围。

客户端提交的 `tenantId` 仅代表请求意图；服务端验证会话、成员关系、权益、动作权限、资源归属和状态后决定是否执行。平台运营身份使用独立权限域，不能仅凭一个超级管理员字符串越过所有租户限制。

首期可使用同库同表隔离，但需通过复合键、唯一约束、关联校验和统一存储边界避免跨租户读写。数据库行级安全可作为技术选项，不以存在 ORM 过滤器来证明隔离已完成。

敏感写操作在事务边界完成授权与资源校验，明确撤权与并发写的顺序；已开始的操作与权限变更的竞争必须有可测试规则。首次实现只承诺已建立测试证据的语义。

## 接口规范

稳定业务码与本地化文本分离；命令支持操作 ID 和幂等语义；分页、筛选、错误封装、审计关联字段由跨端契约统一定义。OpenAPI 是后续 API 结构的单一来源，前端生成类型不手工维护第二份。
