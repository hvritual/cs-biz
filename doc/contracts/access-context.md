# Access Context：租户有效访问上下文

状态：`proposed`；下列接口与 JSON 为设计示例，尚未实现。

## 1. 语义与权威

| 概念 | 例子 | 权威来源 |
| --- | --- | --- |
| Module | `crm`，客户管理模块 | 平台受控模块目录 |
| Entitlement | 租户 A 的 crm 已启用且未到期 | 后端有效权益 |
| Permission | `crm.customer.read` | 后端动作权限定义与成员授权 |
| Data scope | 当前成员允许访问指定客户或点位 | 后端资源范围策略 |
| Navigation | 客户列表入口 | 后端按有效访问生成的菜单投影 + 前端本地页面注册表 |
| Resource state | 已归档合同不可再次激活某操作 | 后端业务规则 |

对每个受保护业务动作，服务端独立判断会话、租户/成员有效性、动作所需模块权益、动作权限、资源范围和状态。缺失任一必要条件时拒绝。

权限来源之间的组合需明确：多个角色可以按既定策略并集，多个必要条件按交集，显式拒绝规则的优先级由具体策略定义。前端辅助函数分别命名 `canAny`、`canAll`；空规则和未知权限默认拒绝。基础企业设置等不要求商业模块的操作要在权限目录明确标记，避免未开通租户无法处理开通或成员恢复。

每项授权必须保留“动作 + 该动作的数据范围”的关联。服务端对具体动作与资源，寻找同时允许该动作并覆盖该资源的有效授权；同一动作可按明确定义的策略合并范围，禁止将不同动作和不同范围分别汇总后做笛卡尔积。例如“全部客户可读 + 负责客户可写”只能得到全部可读、负责部分可写，不能得到全部可写。列表筛选、详情、写入、批量和导出分别使用其动作对应的范围。

## 2. 建议接口形状

建议 `GET /api/v1/tenants/{tenantId}/access-context`：服务端验证当前认证主体与该租户关系后，返回同一逻辑版本下的访问快照。

```json
{
  "subjectId": "user-001",
  "tenantId": "tenant-001",
  "accessVersion": "opaque-version-17",
  "membership": { "status": "active" },
  "entitlements": [
    { "moduleCode": "crm", "status": "active" }
  ],
  "permissions": ["crm.customer.read"],
  "navigation": [
    {
      "name": "crm-customers",
      "path": "/crm/customers",
      "viewKey": "crm.customer.list",
      "titleKey": "menu.crm.customers",
      "order": 100
    }
  ]
}
```

示例只演示已生效的只读权限。扁平 `permissions` 仅用于能力入口展示，不代表该动作已对所有资源授权。数据范围与额度校验不因为该 JSON 中省略了明细就消失，服务端仍负责判断。资源级按钮可消费服务端返回的该资源动作投影，执行时仍重新授权。必要时返回可读的范围说明和额度展示快照，不把客户端传回的范围或余额当作可信授权。

`accessVersion` 是不透明的快照版本，需覆盖成员、角色、权益、范围和相关策略变化。不能由客户端自行产生“更高版本”获得访问，也不能用前端版本替代每次 API 的服务端授权。

## 3. 动态菜单与组件的边界

前端维护 `viewKey -> 已构建组件` 的注册表。服务端只返回经过契约校验的名称、路径、标题键、排序和树结构。未注册 key、重复 route name、非法路径或重定向、异常深度的菜单树应被拒绝并记录可追踪错误。

不能把后端提供的 `component` 字符串直接当成任意文件系统路径或下载地址。不使用 eval、远程 JavaScript 或动态字符串拼接的任意 import。外链和 iframe 需要单独的受控协议，不混入普通业务路由。

Vben backend 路由机制可以作为渲染适配层；本项目公开 API 保持 `viewKey` 等稳定业务键，避免让后端依赖某个 `.vue` 文件目录。Vue Router 支持 `addRoute` / `removeRoute`，新增当前地址对应的路由后还需要正确导航才能生效，详见 [官方动态路由说明](https://router.vuejs.org/guide/advanced/dynamic-routing)。

“某个菜单可见”不能证明对应写权限存在；详情、批量操作和导出必须有自己的权限及数据范围。

## 4. 租户切换与失效流程

建议每个浏览器标签页维护自己的当前租户，请求中显式指定租户并由服务端验证。认证会话与活动租户分离，避免一个标签页切换租户时悄悄改变另一个标签页的写入目标。

1. 进入切换状态，冻结会受上下文影响的提交与导航；为新切换增加本地 generation。
2. 取消旧查询、结束旧订阅，清理旧租户路由、页签、keep-alive 与业务缓存。草稿按用户/租户隔离，必要时明确提醒未保存变更。
3. 加载目标租户的 access context，核对返回主体与 tenantId。任何旧 generation 的晚到结果均丢弃；取消请求本身不能证明服务端写操作没有发生。
4. 同步新租户允许的主题配置、偏好、菜单与路由，跳转有效入口。当前没有业务模块时显示“尚未开通”与有权执行的下一步。
5. 获取失败则保持无业务权限的受控错误状态，不回用旧租户权限作为 fallback。若返回原租户，也须重新获取有效上下文。

缓存键至少包含认证主体、租户与相关访问版本；业务数据不能只用 URL 作为共享 key。退出登录清除租户访问快照，服务端重验先于恢复受保护页面。

## 5. 在线权限变化

角色、成员、权益、数据范围变化后服务端立即按当前有效规则授权。前端通过可靠事件、版本检测或定期刷新获得新快照；刷新失败时不扩展权限。可视状态更新的最大延迟应在 S03 约定并测量，不能仅声称“实时”。

多实例后端需要明确策略缓存的失效或版本检查策略。对敏感写入，在事务或其他可证明的顺序边界重新验证授权，定义撤权和并发操作谁先提交时各自的结果。

旧页面和按钮可以产生短暂陈旧显示，但必须被后端拒绝；前端收到拒绝后立即刷新上下文并呈现原因。不能以 mounted 时一次性移除按钮来证明热更新已生效。

## 6. 错误、提交和结果未知

| 情况 | 建议响应语义 | 前端处理 |
| --- | --- | --- |
| 没有有效会话 | 401，稳定认证错误码 | 重新认证，保留安全的返回位置 |
| 无动作权限、成员停用、模块未开通 | 403 + 可区分业务错误码 | 刷新上下文，按有权范围说明下一步 |
| 跨租户/无权得知的资源 ID | 按统一策略返回 404，避免泄露存在性 | 不显示其他租户数据 |
| 有效主体使用过期前置版本 | 409 + `ACCESS_CONTEXT_STALE` 等稳定码 | 重新核对，不自动重放写请求 |
| 重复幂等键、参数一致 | 返回原操作结果或可查询状态 | 展示同一个结果 |
| 相同幂等键、参数不一致 | 409 冲突 | 明确失败，不执行第二次操作 |
| 网络超时、回执丢失 | 客户端显示结果未知 | 查询已知操作 ID，或使用发起前保存的幂等键恢复；禁止直接等同于业务失败 |

幂等记录的唯一查找键建议为“权限域 + 主体 + 已存在的租户（适用时）+ 操作类型 + Idempotency-Key”。请求摘要单独存入记录，用于比较参数一致性，**不能进入唯一查找键**，否则同一键更换参数会被当作另一条新记录，违反上面的 409 规则。

创建租户时目标租户尚不存在，使用已认证的平台权限域与主体作为作用域。客户端首次提交前生成并保存幂等键；如果第一份回执丢失、尚不知道服务端操作 ID，应能通过这个预先已知的键，在同一权限作用域查询恢复。不能要求只能使用尚未收到的 ID 恢复。

并发重复请求必须通过唯一约束、事务或等效机制落到同一记录；执行中的操作返回可查询状态，完成后返回既有结果。查原操作结果时仍需校验读取权限，不能通过已失效身份读取敏感历史内容。幂等不能替代授权、事务和业务唯一约束。

幂等记录、业务效果与最终结果必须在同一事务或已定义的可恢复边界内提交。涉及外部效果时，单独定义持久化投递和消费幂等；不能在进程崩溃后因为结果记录缺失就再次产生同一业务效果。

## 7. 运行验收出口

采用两个租户、负责人/只读/禁用成员三类状态、已开通/未开通模块构建矩阵。验证完整 UI 与直调 API、列表/详情/写入/批量/导出及后台任务的行为。至少一个真实持久化资源用于证明隔离；只有 Mock 菜单或匿名 fixture 不算 SaaS 权限完成。

版本、执行命令、真实依赖、结果与证据写入对应任务。当前文本和示例尚不提供任何运行通过结论。
